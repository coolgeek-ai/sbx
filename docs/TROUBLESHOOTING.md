# Troubleshooting

## 1. Red warning: "allowInsecure (skip certificate verification) will be removed on 2026-08-01 ..."

**Meaning:** the node (usually Hysteria2 with a self-signed certificate) has "skip certificate verification" enabled. Xray removed that switch, so such nodes can no longer connect through the Xray core.

**Fix**
- Recreate the node with sbx: `sbx add hy2`. Without a domain it generates a self-signed certificate and puts `pinSHA256` in the link. After importing, **do not** enable "skip certificate verification".
- Or add the fingerprint to the existing node: on the server, run
  `openssl x509 -in <cert.pem> -noout -fingerprint -sha256` on the certificate the node uses and enter the `AA:BB:...` value in the node's certificate fingerprint / pinSHA256 field.
- If, after importing into v2rayN, Hysteria2 latency shows -1 and the server log contains `bad certificate` (see [v2rayN #10433](https://github.com/2dust/v2rayN/issues/10433); the root cause is not settled): (1) check that the fingerprint in the node matches the output of `sbx info` (hex with or without colons both work); (2) switch the node's core type between Xray and sing-box in v2rayN and try each; (3) if it still fails, switch to a domain with a real Let's Encrypt certificate (the most reliable option, no fingerprint involved) and report what you saw in an issue.
- Or, if you have a domain, use a real Let's Encrypt certificate (`sbx add hy2 -d your.domain`); no fingerprint is needed.

## 2. Error: `vless without TLS or other encryption is prohibited unless the server address is a private IP or domain`

**Meaning:** the client core decided that the VLESS node has **no transport security at all** (not TLS, not REALITY, and no VLESS Encryption) while the server is a public IP, so it refuses to start.
This was reproduced as-is with Xray-core 26.10.21 (the regression sentinel in `tests/test_e2e.sh`): with `security=reality` removed from the same node the error appears; with it present the result is `Configuration OK`.

**So the cause is usually that the node was parsed as having no security layer.** Common reasons:
1. The link is missing or has corrupted parameters such as `security=reality` (or `pbk` / `sni`), for example because it was truncated or wrapped when copied, or because the script that generated it did not write them all.
2. The node really is a VLESS without TLS (for example `vless-ws` with TLS turned off).

**Check**
- Open the node's edit page in v2rayN / v2rayNG and look at the transport-security field: it must be `reality` or `tls`. If it is `none`, you are in the situation above.
- Compare the link with the output of `sbx info` parameter by parameter. A REALITY link must contain `encryption=none&flow=xtls-rprx-vision&security=reality&sni=…&fp=chrome&pbk=…&sid=…&type=tcp`.
- Recreate the node with sbx and import it again.

> Note: links generated by other scripts may lack some of these parameters. What has been verified here is that the REALITY handshake works end to end with **a sing-box 1.14.4 server + the parameters generated by this script + an Xray 26.10.21 client**.

## 3. REALITY stops working after a client upgrade

Work through these in order:
1. `sbx doctor` — is the service running and the port listening?
2. Is the **TCP** port open in the cloud provider's security group? (Hysteria2 uses **UDP**.)
3. Are all link parameters present? (see above)
4. Can the camouflage target complete a handshake **from the server**: `openssl s_client -connect <sni>:443 -servername <sni> -tls1_3 -alpn h2 </dev/null | grep -E "TLSv1.3|ALPN"`. If not, run `sbx change <name> sni <another-domain>`.
5. In v2rayN, switch the node's core type to sing-box and try once (some users report this works around Xray-core problems on certain networks; see COMPATIBILITY.md).
6. Are the system clocks on the client and the server correct? (`timedatectl`)
7. If nothing helps, open a Bug issue and attach the output of `sbx doctor` and `sbx log`, the **redacted** link, and the client version and log.

## 4. Other

| Symptom | What to do |
|---|---|
| An existing installation from another script is detected under `/etc/sing-box` | Uninstall it with its own uninstaller first, then install sbx; if you are sure it is harmless, set `SBX_FORCE=1` |
| Certificate request fails | The domain must resolve to this server (turn the Cloudflare orange cloud off); port 80 must be free; check the log path printed by the script (`/tmp/sbx-acme.*.log`) |
| The public IP cannot be determined | `SBX_IP=x.x.x.x bash sbx.sh ...` |
| Downloading sing-box fails | The server cannot reach GitHub; override the download location with `SBX_CORE_URL=<direct mirror link>` |
| The service does not start after `sbx update` | The script rolls back to the previous version automatically; afterwards you can run `sbx update <specific version>` |
